# 视频协议记录

以下描述对应研究样本及 `oseasy_helper/video.py` 的实现。字段解释中有明确观察，也有基于样本的推断；没有宣称所有噢易版本都使用同一格式。

## 1. 输入

观察到的广播是 IPv4 UDP 组播。样本中目的端口为 7778，源端口为 8778；CLI 默认前者，只按教师源 IP 过滤，不固定源端口。程序按研究版本中观察到的约定，将教师 IPv4 `A.B.C.D` 映射为组播 `229.1.C.D`，无需组播参数。该规则也用于前序 wrapper，尚未验证适用于其他版本。

每个 UDP 有效载荷先是 16 字节私有头部，后面是 H.264 访问单元的一段。不能把包含该头部的数据直接当成 RTP 或 MPEG-TS 交给 VLC。

头部使用 `struct.unpack_from('<8H', packet)`：

| 字节偏移 | 类型 | 解释 | 实现如何使用 |
| --- | --- | --- | --- |
| 0 | uint16 LE | 样本固定 `0xffff` | 校验魔数 |
| 2 | uint16 LE | 分片编号，从 0 开始 | 按编号排序 |
| 4 | uint16 LE | 本帧总片数 | 集齐才输出 |
| 6 | uint16 LE | 宽度 | 元数据及一致性校验 |
| 8 | uint16 LE | 高度 | 元数据及一致性校验 |
| 10 | uint16 LE | 帧序号，16 位回绕 | 重排和丢帧判断 |
| 12 | uint16 LE | 样本中与宽度相同 | 暂不依赖，语义未完全确认 |
| 14 | uint16 LE | 样本中与高度相同 | 暂不依赖，语义未完全确认 |
| 16… | bytes | H.264 Annex-B 数据分片 | 去头后拼接 |

比如一个人工构造的头部：

```python
struct.pack('<8H', 0xffff, 0, 2, 320, 180, 42, 320, 180)
```

表示帧 42 的第 0 片、共 2 片，标称尺寸 320×180。头部的尺寸不会替代 H.264 SPS；播放器最终按码流参数解码。

## 2. 接收和重组

1. 建立 IPv4 UDP socket，设置复用及接收缓冲区，绑定 `0.0.0.0:udp_port`。
2. 使用 `IP_ADD_MEMBERSHIP` 加入从教师 IP 推导的组播，成员请求明确携带 `--local` 网卡 IPv4。多网卡环境不依赖默认路由猜测。
3. 丢弃源 IP 不等于 `--teacher` 的包。没有应用层认证或加密，源 IP 过滤不构成身份认证。
4. 校验魔数、包长、片号、片数和尺寸。同帧参数必须一致。去掉头部，按帧号和片号缓存，忽略重复片。
5. 按片号连接一个完整帧，按帧序输出。序号距离使用 `(seq - expected) & 65535`，处理 65535 → 0。
6. 缺片或缺帧等待约 0.4 秒后放弃，并丢弃后续依赖帧，直到新的完整关键帧。
7. 超过 2 秒未收到有效结构包后，再次收包会清空旧序号状态；跨度超过 32 帧也会重置等待关键帧。

限制：每个帧最多 4096 片、8 MiB；宽高分别在 16…8192；待处理序号窗口约 32 帧。这些是实现的资源边界，并非已知厂商协议上限。程序不重传，不会修补缺失的 H.264 参考帧。

## 3. H.264 入口

拼接后可见 Annex-B 起始码 `00 00 01` 或 `00 00 00 01`。起始码后的字节与 `0x1f` 相与得到 NAL 类型：

| 类型 | 名称 | 作用 |
| --- | --- | --- |
| 7 | SPS | 视频序列参数 |
| 8 | PPS | 图像参数 |
| 5 | IDR | 不依赖之前图像的解码起点 |
| 1 | 非 IDR slice | 通常需要此前参考图像 |
| 9 | AUD | 访问单元分隔符 |

样本中一个完整关键访问单元同时包含 SPS、PPS、IDR。当前实现也要求三者出现在同一个重组单元里；初次接收、丢帧恢复和新播放器接入都从这样的单元开始。

若另一版本将 SPS/PPS 独立发送，或者一个帧号不再对应一个访问单元，这套假设就需要修改。这里没有完整解析 H.264 slice header；通过 NAL 类型检查也不能单独证明图像可以解码。

## 4. MPEG-TS 输出

脚本直接封装现有 H.264，不做像素解码或再次编码：

```text
UDP → 去除 16 字节头 → 帧内排序/帧间重排 → H.264 Annex-B
    → PES + PTS → MPEG-TS + PAT/PMT/PCR → HTTP → 播放器解码/显示
```

- 每个 TS 包 188 字节，同步字节 `0x47`。
- PAT PID `0x0000`，节目号 1，指向 PMT PID `0x1000`。
- PMT 声明 H.264 的 stream_type `0x1b`，视频 PID 和 PCR PID 均为 `0x0100`。
- 每个帧前重复 PAT/PMT，各自使用 MPEG-2 CRC32；每个 PID 独立维护 continuity counter。
- 视频进入 stream_id `0xe0` 的 PES。视频 PES 长度置零，由后续 PES 起点分隔。
- 如原访问单元没有 AUD，会添加一个 AUD。不会修改原 SPS、PPS 或 slice 数据。
- 样本私有头没有已确认的时间戳。PTS 采用首片到达的单调时钟差换算为 90 kHz，并保证严格递增；PCR 取 PTS 前 4500 tick。不是固定写死一个推测帧率。
- 该时序按所见低延迟样本实现，没有恢复原始 DTS；对 B 帧重排、音视频同步或未知版本不作保证。

裸 H.264 没有容器时间轴，播放器可能推测出与实际到达节奏不同的帧率。这是最终输出 MPEG-TS 的原因。

## 5. HTTP

唯一视频路径是 `/live.ts`，类型 `video/mp2t`，只在 `127.0.0.1` 监听。使用持续响应直至停止，没有固定 Content-Length。最多 4 个播放器；每个连接等待下一完整关键帧，各有 64 项、8 MiB 上限的队列。慢连接达到上限会被关闭，避免无限积压。

HTTP 地址存在与视频可解码是两个不同条件。直播尚未开始时保持等待；直播停止后不重复旧画面、不生成占位视频。重新打开播放器会等待新的关键帧。
